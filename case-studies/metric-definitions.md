# 숫자는 같은 이름이어도 같지 않았다

API 연결은 출발점이었다. 보고서에 쓸 수 있는 숫자인지 확인하는 작업이 더 필요했다.

## 판매매출과 광고 전환매출

광고 플랫폼은 자기 기준으로 구매를 집계한다. 그 수치를 판매 플랫폼의 결제매출에 더하면 같은 구매를 다시 셀 수 있다. 판매와 광고 성과를 별도로 저장하고, 각 보고서가 필요한 값만 읽게 했다.

Meta 응답에서는 구매 지표의 별칭을 중복 합산하지 않도록 처리했다. 네이버 검색광고에서는 전체 전환과 구매 전환을 구분한다. 구매만 집계한 기준이 확인되지 않으면 구매 매출로 쓰지 않는다.

## 결제와 환불

결제·환불·추가 결제를 사건별로 기록한다. 환불이 생겼다고 기존 결제 사건을 지우거나, 잔여 금액의 차이만 보고 환불 시점을 추정하지 않는다. 환불 집계 날짜가 확인되지 않았다면 그 값을 보류한다.

금액은 내부에서 Decimal 또는 문자열로 다루고, 날짜는 한국 시간으로 맞춘다. 소수점 오차와 날짜 경계에서 생기는 차이를 줄이기 위한 선택이다.

## 빈 값과 0

조회가 안 된 날을 0으로 채우면 매출이 없던 날처럼 보인다. 숫자 0, 미확인, 실패, 보류를 구분했다. 대조가 끝난 값과 기간만 입력 후보가 된다.

아래는 실제 실적과 무관한 설명용 예시다.

| 상황 | 보고서에 쓸 값 | 처리 |
|---|---:|---|
| 조회가 완료됐고 실적이 없음 | 0 | 확인한 값으로 입력 후보에 포함 |
| API 조회 실패 | 빈 값 | 실패 기록, 재시도 |
| 값을 받았지만 관리자 기준과 차이가 남음 | 빈 값 | 보류, 원천 대조 |
| 광고 전환매출을 받음 | 별도 광고 지표 | 판매매출에 더하지 않음 |

회원 수도 단순히 누적 회원 수로 설명하지 않았다. 현재 수집 기준은 가입일별 회원 수이며, 조회 시점에 탈퇴한 회원은 제외된다. 이런 기준까지 남겨야 나중에 숫자가 달라져도 이유를 찾을 수 있다.
